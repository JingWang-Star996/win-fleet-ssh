# 10 台 Windows 集群基准测试 · 2026-11-10

> 用确定性任务实测这个 SSH 框架在真实 Windows 集群上的表现：
> 算力分布、收集策略、节点掉线容错。
>
> **这是框架的能力边界测试，不是应用层压测。**

---

## 为什么要测这个

`win-fleet-ssh` 解决的是「把一批 Windows 机器统一管起来」。
但管起来之后，实际用起来会遇到三个必须回答的问题：

1. **机器之间差多少？** 如果差 3 倍，均匀分片就是浪费
2. **必须等最慢那台吗？** 决定能不能做流式返回
3. **掉一台会怎样？** 决定需不需要额外容错机制

这三个问题的答案直接决定上层怎么用这批机器。

## 测试任务

```
SHA-256 哈希链
h(0) = SHA256(seed)
h(i) = SHA256(h(i-1) || i)      i = 1..25,000,000
```

**为什么用这个任务：**

| 要求 | 哈希链如何满足 |
|---|---|
| 确定性 | 结果唯一，任何分歧立刻可见 |
| 单核串行 | h(i) 依赖 h(i-1)，无法并行，测的是纯粹单核性能 |
| 无外部依赖 | 不碰网络/磁盘，排除干扰变量 |
| 可定位 | 每万步存校验点，能精确找出从哪步开始分歧 |

这样测的是**集群协作本身**，不受算法或 IO 影响。

## 结果一：算力分布（10 台并发）

```
10 台同时执行，每台 2500 万步
```

| 指标 | 数值 |
|---|---|
| 成功 | **10 / 10** |
| 墙钟 | **45.5 s** |
| 总计 | **250,000,000 步** |
| 单机耗时 | 27.9 s ~ 42.2 s |
| 单机速率 | 592,506 ~ 897,432 步/秒 |
| 速率差异 | **1.51x** |
| 结果一致性 | **10 台同一哈希** |

### 各节点速率

| 节点 | 步/秒 | 相对最慢 |
|---|---|---|
| OFFCE-PC-SEVER | 897,432 | 1.51x |
| SHA1381 | 737,308 | 1.24x |
| SHA1427 | 729,393 | 1.23x |
| SHA1121 | 714,599 | 1.21x |
| SHA1111 | 702,103 | 1.19x |
| SHA1444 | 701,747 | 1.18x |
| SHA1436 | 697,359 | 1.18x |
| SHA1264 | 691,557 | 1.17x |
| SHA1222 | 634,264 | 1.07x |
| SHA1084 | 592,506 | 1.00x |

**结论：这批机器的性能差异只有 1.5 倍，均匀分片是合理的。**

不需要按性能加权调度 —— 这个结论省掉了一整套复杂度。

## 结果二：收集策略对比

对比「全收齐再返回」和「谁先完成先处理」两种模式。

| 时刻 | 含义 | 时间 |
|---|---|---|
| `T_first` | 第 1 份结果可用 | **30.07 s** |
| `T_90` | 第 9 份结果可用（90%） | 42.08 s |
| `T_all` | 第 10 份结果可用 | 44.64 s |

| 指标 | 数值 | 含义 |
|---|---|---|
| 慢节点带来的额外等待 | **2.56 s（5.7%）** | 必须等最慢那台，代价很小 |
| 首结果提前量 | **14.57 s（32.6%）** | 流式能省掉 1/3 的等待 |

### 这个结果推翻了测试前的假设

原假设是「慢节点会明显拖累整体」，理由是最慢 42s vs 最快 28s。

**实测反驳了这一点**：9 台集中在 34–39 s 这个窄区间里，分布很紧密，不存在极端慢的节点。

**真正的收益在首结果。** 如果上层业务能接受「先看部分结果」，流式收集能提前 14.57 秒。

### 架构建议

| 场景 | 推荐模式 |
|---|---|
| 需要全部结果才能决策 | 批量等待（代价仅 5.7%） |
| 可以渐进展示 | 流式收集（提前 32.6%） |

## 结果三：节点掉线容错

模拟真实场景：机器随时可能关闭、休眠、断网。

```
T+12s  强制终止 SHA1111 上的计算进程
T+15s  强制终止 SHA1444 上的计算进程
T+20s  重启 SHA1111（模拟恢复）
```

| 指标 | 数值 |
|---|---|
| 计划终止 | 2 台 |
| 成功完成 | **8 / 10** |
| **计划外失败** | **0 台** |
| 剩余结果一致性 | **8 台同一哈希** |

### 关键结论

**故障零扩散。**

杀掉 2 台只影响这 2 台，其余 8 台全部正常完成，且结果哈希完全一致。

这意味着：

- 各节点独立执行的设计天然具备容错性
- **不需要额外的故障隔离机制**
- 部分结果（8/10）完全有效，可以直接使用

**对框架设计的意义：** 不需要为"节点掉线"做特殊补偿逻辑，只要上层能接受部分成功即可。

## 能力路由（额外实现）

测试中顺带实现了一个最小能力路由，用于验证「不同机器干不同事」的可行性。

### 单节点匹配：6/6 正确

| 需求 | 路由到 |
|---|---|
| `compute` | OFFCE-PC-SEVER |
| `code` | SHA1264 |
| `summarize` | 工作机 |
| `code` + `review` | SHA1264 |
| `image` | 工作机 |
| `video` | 工作机 |

### 发现的问题：多能力任务无解

```
requires = ['compute', 'image']
→ no single node covers all of ['compute', 'image']
```

**这不是 bug，是架构限制。** 现实任务几乎都需要多种能力：

| 任务 | 需要节点数 |
|---|---|
| 算力 + 生图 | 2 |
| 写码 + 汇总 | 2 |
| 全流程（4 种能力） | 2 |

### 最小方案：贪心集合覆盖

`code/node_router.py` 的 `plan()` 实现了多节点拆分。局限是**只看能力覆盖数量，不看性能差异** —— 曾把 `compute` 分给 691K/s 的节点而非 897K/s 的节点。

## 对框架的使用建议

基于这次实测：

1. **均匀分片就够** — 性能差异仅 1.5x，不必做加权
2. **优先做流式返回** — 首结果能提前 1/3 时间，比优化总量更有感知价值
3. **容忍部分成功** — 掉线零扩散，上层按"完成几台就用几台"设计即可
4. **异构需要能力层** — 但这是上层的事，框架层不需要管
