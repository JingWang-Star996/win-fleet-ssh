# 架构说明

## 整体结构

```
┌─────────────────────────────────────────────────────────┐
│  源端（你的工作机）                                      │
│                                                          │
│  ┌────────────────────────────────────┐                 │
│  │  console2.py  图形控制台            │                 │
│  │  ├── registry2.py   机器台账        │                 │
│  │  ├── heartbeat.py   HTTP 接收端 :18765 │              │
│  │  ├── identity.py    机器码生成      │                 │
│  │  └── probe.py       可达性探测      │                 │
│  └────────────────────────────────────┘                 │
└────────────┬────────────────────────────┬───────────────┘
             │ SSH（下发部署）             │ 心跳（目标机主动推）
             ▼                            ▲
┌─────────────────────────────────────────┴───────────────┐
│  目标机（Windows）                                        │
│                                                          │
│  ┌──────────────────┐  ┌──────────────────┐            │
│  │  sshd 服务        │  │  FleetHeartbeat  │            │
│  │  （或计划任务）    │  │  计划任务         │            │
│  └──────────────────┘  │  每 5 分钟上报    │            │
│                        └──────────────────┘            │
│  ┌──────────────────┐                                   │
│  │  SshGuardian     │  看门狗，每 30 秒探测             │
│  │  计划任务         │  异常时自动修复                   │
│  └──────────────────┘                                   │
└──────────────────────────────────────────────────────────┘
```

## 三条独立通道

设计上刻意让关键能力不互相依赖：

| 通道 | 方向 | 用途 | 依赖 |
|---|---|---|---|
| **SSH** | 源 → 目标 | 下发部署、日常运维 | sshd 正常 |
| **心跳** | 目标 → 源 | 上报身份与地址 | 只要机器活着 |
| **共享队列** | 双向 | 任务下发（可选） | 网络共享可达 |

**为什么这样设计**：SSH 挂了的时候，心跳还能告诉你机器在哪；共享不可达的时候，心跳还能走 HTTP。任意一条通道失败，其它通道仍能提供信息。

## 部署阶段的设计

### 环境探测优先于盲目尝试

`deploy-all.ps1` 在启动 SSH 之前先做两件事：

**探测 1：SYSTEM 上下文是否健康**

```powershell
# 用 SYSTEM 身份跑极简任务，看能否解析自己的 SID
[Security.Principal.WindowsIdentity]::GetCurrent().User.Translate(...)
```

不健康就直接排除「服务方式」——在这类机器上它必然失败。

**探测 2：当前是否已有可用实例**

不只是看端口有没有监听，而是实际读 `SSH-` banner。僵尸进程会让端口保持监听但不响应，只看端口会误判。

### 四级降级链

```
方式 A：Windows 服务
  条件：SYSTEM 上下文健康
  优点：开机自启、不依赖登录、进程崩溃能被系统重启

方式 A2：S4U 计划任务
  条件：A 失败
  优点：用户身份运行（绕开 SYSTEM 问题）、开机触发、不需要密码
  限制：需要账户有密码历史；部分机器注册成功但运行失败

方式 B：登录触发器
  条件：A2 失败
  优点：最兼容
  缺点：需要有人在本机登录桌面

方式 C：独立实例
  条件：以上全失败
  说明：跑在备用端口，用便携版二进制，完全独立于系统组件
```

每一级都用 banner 验证，不看服务状态——服务显示 `Running` 但读不到 banner 的情况很常见。

## 启动切换的安全设计

这是整个框架最核心的设计约束：**永不自断退路**。

### 错误做法（踩过的坑）

```
停旧实例 → 启新方式 → 新方式失败 → 彻底失联
```

### 正确流程

```
┌─────────────────────────────────────────┐
│ 1. 在备用端口 2222 启动候选方案          │
│    ↓                                     │
│ 2. 验证 2222 能读到 SSH- banner          │  ← 硬性闸门
│    ↓ 通过                                │
│ 3. 停掉旧实例（此时新通路已确认可用）     │
│    ↓                                     │
│ 4. 新方案接管生产端口 22                 │
│    ↓                                     │
│ 5. 持续监控 60 秒                        │
│    ↓ 异常                                │
│    回滚到旧方式                          │
└─────────────────────────────────────────┘
```

对应实现见 `ssh-start-adaptive.ps1` 的 `Start-CandidateOnProbePort` 函数。

## 运行时自愈

### 守护进程

```
每 30 秒
  ↓
探测 22 端口能否读到 SSH- banner
  ↓ 连续 2 次失败
触发修复
  ↓
修复 1：重启当前启动方式
  ↓ 失败
修复 2：前台进程兜底
  ↓ 失败
降低频率，等下一轮（避免疯狂重试）
```

实测：杀掉 sshd 后 40 秒内恢复。

**单实例锁**：用命名 Mutex 保证全机只有一个守护进程。计划任务每 10 分钟触发一次，如果没有锁会堆积。

### 心跳自愈

心跳脚本同样有单实例锁，并且支持配置热更新——每轮检查 `heartbeat-target.txt`，地址变了自动切换，不需要重启任务。

## 身份识别设计

### 机器码

```python
seed = "guid:" + MachineGuid
if physical_mac:
    seed += "|mac:" + normalize(physical_mac)
machine_id = sha256(seed).hexdigest()[:16]
```

**为什么是组合而不是单一字段**

| 字段 | 单独使用的问题 |
|---|---|
| `MachineGuid` | 克隆机器会重复 |
| MAC | 换网卡会变；虚拟网卡在机器间重复 |
| BIOS 序列号 | 常是占位值，可能被工具改写 |
| 主机名 | 可被重命名 |

`GUID + MAC` 组合：GUID 保证重装系统前稳定，MAC 区分克隆机。

### 虚拟网卡过滤

```
VMware     00:50:56, 00:0C:29, 00:05:69
VirtualBox 08:00:27
Hyper-V    00:15:5D
```

这些前缀的 MAC 不参与哈希，因为它们在所有虚拟机上可能相同。

## 数据存储

`console/data/registry.json`：

```json
{
  "machines": {
    "<machineId>": {
      "hostname": "...",
      "identity": { "machineGuid": "...", "mac": "...", ... },
      "addresses": [
        { "host": "...", "port": 22, "kind": "lan",
          "lastOk": "...", "failCount": 0, "note": "" }
      ],
      "deployed": true,
      "deployMode": "service",
      "online": true,
      "onlineAddress": "..."
    }
  },
  "audit": [
    { "time": "...", "machine": "...", "action": "...", "result": "...", "detail": "..." }
  ]
}
```

**地址簿支持多地址**：一台机器可以同时记录 LAN、Tailscale、备用端口等多个地址，探测时逐个尝试，任一可用即认为在线。这解决了多网卡、多网络环境的问题。

## 配置项管理

配置优先级：

```
命令行参数  >  配置文件  >  环境变量  >  内置默认值
```

心跳地址在 `deploy/heartbeat-target.txt`（一行），改成新地址后重新部署即可。

对配置文件的容错：

- 带 BOM → 自动清理
- 首尾空格 → 自动去掉
- 文件不存在 → 跳过心跳安装，不报错

这几种情况都实测验证过，因为记事本保存 UTF-8 默认加 BOM，很容易踩到。

## 并发与超时

| 操作 | 超时 | 重试 |
|---|---|---|
| TCP 连接探测 | 2-6 秒 | 无 |
| SSH 登录 | 10-12 秒 | 无 |
| banner 读取 | 3-5 秒 | 最多 12 次（间隔 2 秒） |
| 服务启动等待 | 5 秒 | 无 |
| 端口释放等待 | 1 秒 × 15 | 有 |
| 稳定性观察 | 10 秒 × 6 | 无 |

**原则**：探测类操作宁可短超时快速失败，也不要长超时卡住流程。因为有降级链，失败可以走下一级。
