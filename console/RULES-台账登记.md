# 机器台账登记规则

> 2026-11-06 由用户明确确立，优先级高于任何自动发现逻辑。

## 核心规则：以回传为准

**台账里的机器只能来自两种来源：**

1. **用户明确告知**（给了 IP / 主机名 / 让去部署）
2. **目标机主动回传**（心跳上报到 18765，或部署脚本回传结果）

**除此之外一律不登记。**

## 禁止行为

- ❌ **扫网段发现主机后自动加进台账**
  扫描结果只能作为「待用户确认的线索」，不能直接写成正式记录。
- ❌ 仅凭端口开放、主机名形似（如 `SHA####`）、反解域名等间接证据推断「这是我们的机器」
- ❌ 把猜测标成事实写进 `notes` 或审计日志

## 为什么

2026-11-06 事故：

我在扫 `192.0.2.0/24` 时发现 `192.0.2.56` 和 `192.0.2.159` 的 2222 端口有监听，
反解出 `SHA1439.local` / `SHA1349.local`，主机名形似用户的命名风格，
就**直接登记成了 SHA1439 / SHA1349**，并写进控制台。

用户看到后说：「SHA1439 和 SHA1349 从哪来的，我都不知道有他们。」

这两个主机名虽然是真实存在的机器，但**用户从未告知过它们是自己的机器**。
2222 端口有监听也可能只是别的软件在用。

**教训：间接证据不等于事实。登记台账是在写用户的资产清单，
必须用户确认或机器自己证明身份（心跳上报机器码）。**

## 正确做法

如果扫描发现可疑主机：

1. 只在**当次对话里报告**「发现 X 台可疑主机，端口特征如下」
2. 明确标注「未确认，仅供参考」
3. **等用户说「这台是我的」或「去部署它」之后**，才写进台账
4. 或者等它自己发心跳上来（此时有真实机器码，是真凭据）

## 心跳是权威来源

心跳上报带着 `MachineGuid + MAC` 算出的机器码，这是机器自己在证明身份。
**只有这种带机器码的回传，才能直接建台账记录。**

扫描只能产生「线索」，不能产生「记录」。
