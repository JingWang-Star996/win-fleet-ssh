## 二、为什么不能简单地把 10 台都塞进 Unity

`STATUS.md` 明确写着：

> **根为唯一源码写入者**；Unity 自动升级也算写入阶段，期间不并行修改同一工程。

所以：

- ❌ 不能让多台机器同时改 `projects/TPM-Reconstruction-r1`
- ❌ 不能让多台同时跑 Unity（会抢文件锁、产生不可复现状态）
- ✅ **可以**多台并行做**只读分析**
- ✅ **可以**多台并行生成**独立产物**（shader 源码、分析报告）

**这就是任务设计的分界线。**

---

## 三、任务拆解：三层

### 第一层：并行只读分析（8 台，安全）

**目标**：把 110 个占位 shader 逐个分析清楚，产出可直接用于重写的规格。

每个 shader 需要分析：

```
输入：shader 名字 + 原游戏资源目录（只读）
产出：一份分析报告，含
  - 原 shader 的语义（从名字 + 使用它的材质推断）
  - 需要哪些属性（Properties 块）
  - 光照模型（Lit / Unlit / 特殊）
  - 参考实现（URP 里最接近的 shader）
  - 重写难度评估
```

**分片策略**：8 台 × 约 14 个 shader/台

按 T1→T5 优先级排序后顺序切片，保证高优先级的先被分析。

### 第二层：串行整合（1 台，本机）

**目标**：把 8 台的报告汇总，生成可执行的重写计划。

```
输入：8 份分析报告
产出：
  - 合并后的规格表（按优先级）
  - 重写顺序建议（依赖关系）
  - 每批的验收标准
```

**必须是串行**，因为它要写工程目录。

### 第三层：验证（1 台，隔离）

**目标**：对生成的重写 shader 做静态验证。

```
输入：重写后的 shader 源码
产出：
  - 语法检查（能否被 Unity 编译）
  - 属性完整性（材质引用的属性是否都有）
  - 与原始占位文件的 diff
```

**在隔离目录做**，不碰生产工程。

## 四、调度机制设计

### 为什么要空闲监控

用户要求「主机进行算力闲置状态监控，进行动态负载调度，避免机器闲置」。

实测数据支持这个需求：

- 各机速率 592K ~ 897K 步/秒（差 1.51x）
- 但 T2 测试显示：9 台集中在 34-39s，分布紧密

**真正的闲置风险不在快慢，而在任务粒度**：
如果一个任务要 40 秒，另一个 5 秒，那 5 秒的机器就会闲 35 秒。

### 调度器设计

```
┌──────────────────────────────────────┐
│  Dispatcher                          │
│  - 任务队列（按优先级）               │
│  - 节点池（含负载与在线状态）         │
│  - 空闲检测（心跳 + 负载采样）        │
└──────────────┬───────────────────────┘
               ↓ 派发
┌──────────────┴───────────────────────┐
│  Worker（每台机器）                   │
│  - 领任务                             │
│  - 执行                               │
│  - 回报                               │
└──────────────────────────────────────┘
```

**核心逻辑**：

```python
while 还有任务:
    空闲节点 = [n for n in 节点池 if n.在线 and n.负载 < 阈值]
    if 空闲节点:
        任务 = 队列.取最高优先级()
        派给最合适的空闲节点(任务, 空闲节点)
    else:
        等待任一节点回报
```

**关键指标**：
- 节点利用率（忙碌时间 / 总时间）
- 任务平均等待时间
- 队列长度随时间变化
