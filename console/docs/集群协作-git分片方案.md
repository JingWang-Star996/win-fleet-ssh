# 集群协作方案：Git 分片 + 目录认领

> 目标：让 10 台机器并行修 shader，但**任何人都不成为瓶颈**。
> 关键设计：把「谁能改哪个文件」变成硬规则，冲突在物理层面就不可能发生。

---

## 一、当前的真实工作量（已核实，不是估算）

先纠正一个关键误判：

| 指标 | 数值 | 说明 |
|---|---|---|
| 工程 shader 总数 | 390 | 全 `Assets/` 递归扫描 |
| 其中占位 | 230 | 含 `DummyShaderTextExporter` 标记 |
| 已修复 | 65 | URP 官方，与 upstream **逐字节一致** |
| 真实实现 | 160 | 无 Dummy 标记 |

**已修复的 65 个验证结论：`完全一致`，差异行 0。**
说明「从 Unity 官方包导出」这条路是正确的、零风险的。

### 剩余 230 个的性质（重要）

```
无官方对应（自研）: 230 个，全部
```

也就是说剩下这 230 个**都只能自己写**，没有现成源码可抄。

### 但它们的起点不是零

上一轮状态分析（295 个样本）显示：

| 状态 | 数量 | 含义 |
|---|---|---|
| 真空壳 | 0 | 完全没内容 |
| 半空壳 | 41 | 有编译块但无输出 |
| 占位输出 | 1 | 返回常量 |
| **基础实现** | **143** | 有采样逻辑，缺细节 |
| **较完整实现** | **110** | 有多段逻辑 |

**86% 已有可编译代码。** 所以工作性质是「补细节」，不是「从零写」。

这直接决定了协作方式：**不是让 10 台各写一堆新代码再合并（那必然冲突），
而是让 10 台各自补齐自己负责的文件（天然无冲突）。**

---

## 二、为什么不采用「大家往一个分支提交然后合并」

你提到的「部署 git 让大家提交合并」是最自然的想法，但对这个任务不合适：

| 问题 | 后果 |
|---|---|
| 230 个 shader 分散在 40+ 个目录 | 分支合并时目录结构冲突概率极高 |
| 每个 shader 改动都是「重写整个文件」 | 行级 diff 合并基本无意义，全是冲突 |
| Unity 的 `.meta` 必须与文件同改 | 忘记同步 meta 会导致 GUID 引用断裂 |
| 合并冲突需要人判断 | 又回到「一个人当瓶颈」 |

**根本原因：这个任务的并行单元是「文件」，不是「代码行」。**
文件级并行不需要 git 的合并能力，只需要「谁改哪个文件」的明确归属。

## 三、方案：目录认领 + 分片提交

### 3.1 核心机制：认领制

```
shader-ownership.json    ← 谁负责哪些目录/文件（单一事实源）
```

每台节点启动时：
1. 读 `shader-ownership.json`，找出归自己的条目
2. 只改这些文件，绝不碰别人的
3. 完成后写自己的 `outbox/<hostname>/done.json`
4. 报告完成清单

**冲突在启动时就被排除了**，因为归属是预先分好的，不是运行时抢的。

### 3.2 分片方式：按目录 + 负载均衡

实测各目录的占位数量：

| 目录 | 占位数 | 建议分配 |
|---|---|---|
| `Data/Art/Shaders` | 64 | 拆成 4 片，16 个/片 |
| `Shader/`（根） | 56 | 拆成 4 片，14 个/片 |
| `Plugins/TPS.ShaderSrc`（含子目录） | 42 | 拆成 3 片 |
| `Code/**/Shaders` | 27 | 1 片 |
| `Plugins/TextMesh Pro/Shaders` | 14 | 1 片 |
| 其他零散 | 27 | 1 片 |
| **合计** | **230** | **14 片** |

10 台机器跑 14 片：快的机器做完自己那片后**再领下一片**（动态补位），
避免「快的闲着、慢的拖着」。

### 3.3 Git 怎么用：只用于「提交与留痕」，不用于合并

```
main                        ← 唯一集成分支，只由编排器写
├── shard/01-data-art-a     ← 节点 A 的分支，只含自己那片的改动
├── shard/02-data-art-b     ← 节点 B
└── ...
```

流程：

```
1. 编排器从 main 建出 N 个 shard 分支（每个分支只放该片的初始文件）
2. 节点 clone 自己的 shard 分支，在本地改
3. 节点 commit + push 自己的分支
4. 编排器按顺序 cherry-pick / merge 到 main
   ↑ 因为各分支改的文件完全不重叠，merge 永远不会冲突
```

**关键：因为文件不重叠，merge 是纯机械操作，不需要人判断。**
编排器可以用脚本自动合并，不构成瓶颈。

### 3.4 与 Unity 单写入者的关系

`AGENTS.md` 要求「根为唯一源码写入者」，原因是**避免 Unity 同时改同一工程**。
本方案不违反这条：

- 节点**不启动 Unity**，只做文本编辑与静态校验
- 节点改的是自己 clone 的副本，不是生产工程
- 编排器把合并后的结果一次性落到生产工程（串行，只有一次写入）
- Unity 导入/编译仍由编排器串行触发

**所以「并行编辑」与「串行写入生产」可以共存。**

## 四、具体实施

### 4.1 阶段一：建立骨架（编排器做，10 分钟）

1. 在生产工程根初始化 git 仓库（`.gitignore` 已有，直接用）
2. 首次提交：只提交代码与元数据，不含 Library/（已 ignore）
3. 推送裸仓库到网盘：`\\192.0.2.101\深圳公用文件夹\_agent-queue\repo\shaders.git`
4. 生成 `shader-ownership.json`（14 片 × 230 个文件）

### 4.2 阶段二：节点拉取与认领（每台 2 分钟）

每台节点：
```bash
git clone //192.0.2.101/.../shaders.git shard-XX
cd shard-XX
# 读 ownership，确认自己负责哪些文件
```

### 4.3 阶段三：并行修改（节点自主）

节点对每个文件：
1. 读占位内容，提取 `Properties` 与 `Pass` 结构
2. 按用途补全实现（保留原属性名与结构）
3. 静态校验（括号配对、编译块闭合、入口函数存在）
4. commit

### 4.4 阶段四：回收与集成（编排器）

1. 等各分支 push
2. 按片号顺序 merge（无冲突）
3. 落生产工程
4. 触发 Unity 编译验证
5. 把失败项重新分片给节点

## 五、为什么这个方案不会让我成为瓶颈

| 环节 | 谁做 | 是否串行 |
|---|---|---|
| 生成认领表 | 编排器 | 一次，10 分钟 |
| 修改 230 个文件 | **10 台并行** | 否 |
| 静态校验 | 节点自查 | 否 |
| merge 分支 | 脚本自动 | 是，但每片 < 1 秒 |
| Unity 编译 | 编排器 | 是，但只有一次 |

**唯一的串行环节是 Unity 编译，那是物理约束（同一工程不能并发导入），
不是我的人为瓶颈。**

如果 230 个文件的工作量是 X 人时，10 台并行后墙钟时间约 X/8（考虑慢节点）。
编排器只需两次动作：发认领表、收分支合并。

## 六、如果节点能力不足怎么办

节点跑的是 `dsh headless`，理解力有限。所以要给每个 shader 附**明确规格**：

```json
{
  "file": "Assets/Code/Core/Shaders/UI/UI_Additive.shader",
  "shaderName": "Two Point/UI/Additive",
  "currentState": "基础实现",
  "properties": ["_MainTex", "_Color", "_StencilComp", ...],
  "missingFeatures": ["UGUI stencil 测试", "ColorMask", "AlphaClip"],
  "reference": "UGUI 默认 UI/Default shader",
  "mustPreserve": ["属性名", "Pass 数量", "Tags"]
}
```

**节点不需要创造性，只需要按规格补全。** 这样即使节点能力有限也能产出可用结果。

## 八、需要你确认的三点

1. **裸仓库放网盘还是放本机？**
   放网盘：所有节点都能 push，但 Windows SMB 上跑 git 可能有锁问题（需测）
   放本机：本机必须常开，且要开 SSH 给节点 push

2. **是否允许节点完全不启动 Unity？**
   我按「不启动」设计。若需要节点自验，得给每台装 Unity（体积与授权都大）

3. **230 个的优先级**
   我建议按「世界可见」优先：T1 世界几何 → T2 角色 → 三分支其他
   你要不要按别的顺序？
