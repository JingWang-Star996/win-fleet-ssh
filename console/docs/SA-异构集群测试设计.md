# SA 异构 Agent 集群测试：A / C 双方案实测设计

> 目标不只是"跑通"，而是回答一个架构问题：
> **能否让一台机器作为独立 Agent 节点参与任务，未来形成 MoE 式的合力？**

---

## 一、先明确"异构节点"在这套架构里意味着什么

你描述的目标形态：

```
任务：做一个完整的游戏小 demo
  ↓ 拆解
  策划节点（写设计文档）
  程序节点（写代码）
  美术节点（生图/生视频）
  测试节点（跑验证）
  ↓ 汇总
  完整交付物
```

**关键点：每个节点有自己的"专长"，不是干同样的事。**

### 现有 SA 能做到什么、做不到什么

| 能力 | 现状 | 说明 |
|---|---|---|
| 拆解任务 | ✅ 能做 | eval + policy 决定接不接、怎么拆 |
| 分派任务 | ⚠️ 只能通过 prepare | 唯一跨机接口 |
| 节点专长区分 | ❌ 没有概念 | SA 不知道哪台机器会干什么 |
| 节点能力发现 | ❌ 没有 | 要先手工维护一张"能力表" |
| 结果汇聚 | ⚠️ 弱 | 靠回帖或写文件 |
| 节点间协作 | ❌ 没有 | 没有消息总线 |

### 结论

**SA 现在能做的是"派活"，不是"编排异构集群"。**

要测出差距，测试任务必须包含**真实的异构分工**，而不是 10 台跑同一个算法。

---

## 二、测试任务设计：**一个需要多角色协作的真实小任务**

### 任务：生成一份"集群能力报告"

选这个任务因为它：

1. **每个节点贡献不同**：有的算数据、有的写代码、有的生图、有的做汇总
2. **产物可验证**：最终报告有明确结构，缺项立刻可见
3. **不依赖外部服务**：图片生成可以先用占位，避免被平台限流卡住
4. **能测协作**：节点之间必须传递中间结果

### 角色划分（按实际机器能力）

| 角色 | 分配到 | 职责 | 产出 |
|---|---|---|---|
| **数据节点** | SHA1084/1111/1121/1222/1381/1427/1436/1444 | 跑 hashchain 基准，报告算力 | 每台一个 JSON |
| **代码节点** | SHA1264（开发机） | 写一个脚本，把 8 份 JSON 汇总成统计表 | summary.py + 结果 |
| **汇总节点** | OFFCE-PC-SEVER | 生成最终 Markdown 报告，检查完整性 | report.md |
| **图片节点** | 本机（有图片平台） | 生成报告配图 | png |
| **编排节点** | 本机 SA | 拆解、分派、监控、汇总 | 工单流转记录 |

**注意：这个分工是"模拟"的——8 台数据节点的能力其实相同。**
真正异构（有的会生图、有的会写代码）需要节点上报能力，而 SA 现在没有这个机制。

**所以测试要分两层：**

- **A 层（今天能做的）**：验证 SA 能否把任务拆给不同节点并收齐结果
- **C 层（要新建的）**：验证"节点能力注册 + 按能力路由"的可行性

## 三、A 方案：SA 工单驱动（不改 SA 代码）

### 流程

```
1. 本机建 10 个 GitHub Issue（每台一个）
   Issue 内容：跑 hashchain，N=2500万步，把结果写到指定路径
        ↓
2. SA 轮询发现 → eval 判定 → 建工单
        ↓
3. executor.prepare 执行：
   ssh 到目标机 → 确保 hashchain.js 存在 → 启动计算 → 等待完成 → 回收 JSON
        ↓
4. worker（本机）读取回收的 JSON，校验结果
        ↓
5. 回帖到 Issue，附结果摘要
        ↓
6. 收齐 10 份后，本机汇总
```

### 要收集的数据

```json
{
  "issueNumber": 12,
  "hostname": "SHA1084",
  "timeline": {
    "issueCreatedAt": "...",
    "firstPollAt": "...",        // 轮询延迟
    "pollLatencyMs": 3421,
    "evalStartedAt": "...",
    "evalFinishedAt": "...",
    "evalDurationMs": 2100,
    "evalVerdict": "accept",
    "ticketCreatedAt": "...",
    "prepareStartedAt": "...",
    "prepareFinishedAt": "...",
    "prepareDurationMs": 62000,  // 含远端计算时间
    "workerStartedAt": "...",
    "workerFinishedAt": "...",
    "replyPostedAt": "...",
    "totalMs": 78000
  },
  "remote": {
    "elapsedMs": 51234,          // 远端纯计算
    "resultHash": "a3f5...",
    "stepsPerSecond": 488000
  },
  "verification": { "hashMatch": true }
}
```

### A 方案能回答的问题

| 问题 | 指标 |
|---|---|
| GitHub 轮询有多快？ | pollLatencyMs |
| eval 判定准不准？ | 10 次判定的人工核对 |
| prepare 能撑多长任务？ | prepareDurationMs vs 超时上限 |
| 3 并发下 10 个任务要多久？ | 总墙钟时间 |
| 失败率多少？ | 失败工单数 |

### A 方案的预期瓶颈

**我预判会有三个问题，测试就是去验证：**

1. **prepare 超时**：远端计算 50 秒，加 ssh 开销，可能触顶
2. **串行排队**：maxWorkers=3，10 个任务要 4 轮
3. **结果回流麻烦**：SA 的 worker 在本机，要读远端文件必须 prepare 时拉回来

## 四、C 方案：节点 Agent 化（新建能力层）

这是我们真正想要的形态：**每台机器跑自己的 dsh，作为独立 Agent 接收任务**。

### 核心思路

```
SA（编排层）
  ↓ 不是 ssh 派命令，而是「发任务给节点 Agent」
节点 Agent（每台机器上的 dsh）
  ↓ 自己理解任务、自己执行、自己回报
```

### 设计要点

**1. 节点 Agent 需要一个"接收任务"的接口**

现有 dsh 有 headless 模式：
```bash
dsh headless "任务描述"
```

所以最小可行方案是：
```
SA prepare → ssh 到节点 → dsh headless "任务" → 取 stdout
```

这比直接 ssh 跑脚本强，因为：
- 节点 Agent 能理解模糊指令
- 能自己决定用什么工具
- 能处理意外情况

**2. 节点需要上报能力（能力注册表）**

维护一份 `nodes.json`：

```json
{
  "SHA1264": {
    "host": "192.0.2.37",
    "role": "developer",
    "capabilities": ["code", "review", "debug"],
    "models": ["skyunion-deepseek"],
    "maxConcurrent": 2
  },
  "OFFCE-PC-SEVER": {
    "host": "192.0.2.229",
    "role": "aggregator",
    "capabilities": ["summarize", "report"],
    "models": ["skyunion-deepseek"]
  }
}
```

**3. 任务路由：按能力匹配**

```python
def route(task):
    need = task.requires  # ["code"]
    candidates = [n for n in nodes if set(need) <= set(n.capabilities)]
    return pick_least_loaded(candidates)
```

**4. 结果汇聚：统一的产物目录**

每台机器把产物写到一个约定的共享位置（或回传本机）：
```
artifacts/
   task-id/
     SHA1084.json
     SHA1264.py
     report.md
```

### C 方案测试任务（真正异构）

```
任务：为一款小游戏生成"技术可行性报告"

拆解：
  1. 策划节点（OFFCE）→ 写需求摘要
  2. 数据节点（8 台）  → 实测各机算力，产出数据表
  3. 代码节点（SHA1264）→ 写一个脚本分析数据
  4. 图片节点（本机）   → 生成一张架构图
  5. 汇总（OFFCE）     → 合成最终报告

依赖关系：
  1 → 2 → 3 → 5
          4 ↗
```

**这个任务的关键：节点之间必须传递产物。** 这正是测"合力"的核心。

## 七、我对"MoE 式合力"的判断（先说结论）

**技术上是可行的，但有三个前提现在没有：**

1. **节点能力发现**：机器要能自报"我会什么"，现在只能手工维护
2. **任务分解质量**：SA 的 eval 现在只能判断"接不接"，不能做"拆成几个子任务 + 指定角色"
3. **结果融合**：多个节点的产物如何合成一个答案，没有机制

**最现实的路径：**

```
第一步（今天测）：SA 派活 → 节点各自干 → 人工汇总
第二步（下次）：节点 agent 化 → 能理解任务 → 自动汇总
第三步（未来）：加能力注册 + 任务分解 → MoE 式调度
```

**先测第一步，用数据决定值不值得走第二步。**
