# 异构 Agent 集群：测试套件设计

> 目标：为「动态异构个人算力集群」这个开源项目，设计一组**能分别隔离单一变量**的测试任务。
> 每个测试回答一个架构问题，产出一组可对比的数据。

---

## 零、先说清目标形态

你要的不是"多台机器跑同一个任务"，而是：

```
                  ┌─────────────────────────┐
                  │      任务到达            │
                  └───────────┬─────────────┘
                              ↓
                  ┌─────────────────────────┐
                  │  拆解 + 能力匹配         │
                  │  "这个任务需要什么能力"   │
                  └───────────┬─────────────┘
                              ↓
        ┌──────────┬──────────┼──────────┬──────────┐
        ↓          ↓          ↓          ↓          ↓
   [有显卡]   [本地 LLM]  [生图]    [云端账号A] [云端账号B]
   跑推理     跑 token   出素材    分摊限速    分摊限速
        └──────────┴──────────┼──────────┴──────────┘
                              ↓
                  ┌─────────────────────────┐
                  │      结果融合            │
                  └─────────────────────────┘
```

**四个本质特征，缺一不可：**

| 特征 | 含义 | SA 现状 |
|---|---|---|
| **异构** | 节点能力不同 | ❌ 无概念 |
| **动态** | 节点随时上下线 | ❌ 假设固定 |
| **分摊** | 多账号并行突破限速 | ❌ 单账号 |
| **融合** | 多节点产物合成答案 | ❌ 无机制 |

**所以测试必须围绕这四个特征设计，而不是围绕"跑得快不快"。**

---

## 一、测试套件的设计原则

### 原则 1：一个测试只改一个变量

如果同时测"能力路由"和"动态上下线"，出问题时分不清是哪一环。

### 原则 2：每个测试都要有对照组

没有对照，数据无法解释。例如"多账号并发快 3 倍"——要和单账号串行比才有意义。

### 原则 3：指标必须可复现

用确定性任务（哈希链、固定输入），避免 LLM 随机性污染数据。

### 原则 4：失败路径也要测

开源给别人用，别人的机器一定会掉线。**掉线时的行为比正常时更重要。**

---

## 二、六个测试任务

### T1：能力路由正确性

**问的问题**：任务声明自己需要能力 X，能否 100% 路由到有 X 的节点？

**任务设计**

准备 6 类任务，每类声明不同能力需求：

| 任务 | 声明需要 | 期望落到 |
|---|---|---|
| `compute-hash` | `compute` | 8 台算力节点任一 |
| `write-script` | `code` | SHA1264 |
| `summarize` | `summarize` | OFFCE 或本机 |
| `make-image` | `image` | 本机 |
| `review-code` | `code`+`review` | SHA1264 |
| `full-report` | `summarize`+`report` | OFFCE |

**指标**
- 路由准确率（正确落到有能力的节点 / 总数）
- 无解任务的处理（要求 `video` 但集群没有 → 应该明确报错而不是乱派）
- 路由决策耗时

**为什么重要**：这是异构集群的地基。路由错了，后面全错。

**实现成本**：低。需要能力注册表 + 简单匹配函数。

---

### T2：快慢节点混跑，慢节点不能拖累整体

**问的问题**：一个 3 倍慢的节点，会不会让整个任务等到它完成？

**任务设计**

```
10 台同时跑同一任务（hashchain 2500 万步）
每台完成即刻上报，不等待其他节点
```

**对比两种收集模式**

| 模式 | 行为 |
|---|---|
| 批量等待 | 全部完成才返回（当前基线就是这种：45.5s） |
| 流式收集 | 谁先完成先处理，慢的继续跑 |

**指标**
- 首结果时间（第一次拿到结果的时刻）
- 90% 结果时间（第 9 台完成的时刻）
- 全部结果时间
- 慢节点造成的额外等待（全部 − 90%）

**为什么重要**：动态集群里慢设备很常见（手机、老笔记本）。如果必须等最慢的，用户体验会很差。

**已验证数据**（本次基线）
```
最快 27.9s  最慢 42.2s  → 慢节点让整体多等 14.3s
如果用流式：第 9 台在约 40s 就能拿到，只差 2s
```

**实现成本**：低。改收集逻辑即可。

---

### T3：动态成员 — 节点中途掉线

**问的问题**：跑到一半拔掉一台机器，任务能否完成并给出清晰结论？

**任务设计**

```
10 台跑 hashchain
T+15s 时强制杀掉 2 台的进程（模拟掉线）
观察剩余 8 台的行为与最终报告
```

**指标**
- 掉线检测耗时
- 剩余节点是否继续（应继续）
- 最终报告是否明确标出"2 台未完成"
- 部分结果是否有价值（8/10 的结果本身是对的）

**为什么重要**：你说了机器是动态的，有时有有时没有。开源用户更是如此——笔记本合盖、手机锁屏都是掉线。

**实现成本**：中。需要超时检测 + 部分成功语义。

---

### T4：多账号分摊限速（最有价值）

**问的问题**：用 N 个账号并行，能否把云端吞吐提升接近 N 倍？

**任务设计**

```
单账号串行：  1 个 key，发 M 个请求，测量总耗时 T1
多账号并行：  N 个 key，各发 M/N 个请求，测量总耗时 T2

加速比 = T1 / T2
```

**关键设计**

用户明确提到"云端对单机器有限速，把这些机器的账号运用起来，让限速被更快的打开"。

所以测试要区分两种限速维度：

| 限速维度 | 是否受多账号影响 |
|---|---|
| 按 API key 限速 | ✅ 多 key 有效 |
| 按 IP 限速 | ❌ 多 key 无效（同一出口 IP）|
| 按账号（组织）限速 | ⚠️ 取决于实现 |

**这决定了架构设计**：如果是按 IP 限速，那多账号没用，必须在不同网络出口上部署节点。

**指标**
- 单账号吞吐（请求/秒）
- N 账号吞吐
- 实际加速比 vs 理论加速比
- 429 错误率随并发的变化
- **关键**：吞吐在多少并发时达到平台（Little's Law 拐点）

**实现成本**：中。需要多个有效 key + 并发压测框架。

**⚠️ 前置条件**：需要你提供多个不同的有效账号。目前 10 台机器共用同一个 skyunion key，测不出分摊效果。

---

### T5：跨节点产物传递

**问的问题**：A 的产出能否可靠传给 B 作为输入？

**任务设计**

```
节点 A（SHA1264）：写一个分析脚本 analyze.py
        ↓ 产物传递
节点 B（OFFCE）  ：用 analyze.py 处理数据，出报告
        ↓
本机            ：校验报告完整性
```

**传递方式对比**

| 方式 | 实现 | 优点 | 缺点 |
|---|---|---|---|
| 经本机中转 | A → 本机 → B | 简单可控 | 本机是瓶颈 |
| 直传 scp | A → B 直连 | 快 | 要处理认证 |
| 共享存储 | 都读写同一目录 | 解耦 | 需要共享盘 |
| Git 仓库 | 产物提交到分支 | 天然版本化 | 慢 |

**指标**
- 传递耗时（分方式）
- 产物完整性（大小/哈希校验）
- 失败重传率

**为什么重要**：MoE 式合力的前提是产物能流动。传不动就没有"合力"。

**实现成本**：中。

---

### T6：弹性扩缩 — 中途加机器

**问的问题**：任务跑到一半加入新节点，新节点能立即分担工作吗？

**任务设计**

```
T+0s   3 台开始跑 1 亿步
T+20s  加入 7 台
观察：新节点是否接到剩余工作？总耗时缩短多少？
```

**这里有个关键设计选择：任务可不可再分？**

| 任务类型 | 中途加机器 |
|---|---|
| 可分片（hashchain 区间搜索） | ✅ 能立即分担 |
| 不可分（一次 LLM 调用） | ❌ 只能等下一个任务 |

**这直接决定了架构能支持什么任务。** 测试要明确区分。

**指标**
- 新节点加入后多久接到工作
- 总耗时 vs 不用新节点
- 加速是否符合理论（剩余工作 / 新并发数）

**实现成本**：高。需要任务可切片 + 动态分配。

## 三、优先级与执行顺序

| 优先级 | 测试 | 理由 | 今晚能做 |
|---|---|---|---|
| P0 | T1 能力路由 | 地基，错了全错 | ✅ 能 |
| P0 | T2 快慢混跑 | 已验证有 14.3s 可优化空间 | ✅ 能 |
| P1 | T3 动态掉线 | 开源场景必现 | ✅ 能 |
| P1 | T5 产物传递 | 合力的前提 | ✅ 能 |
| P2 | T4 多账号分摊 | 需要多 key | ⚠️ 缺条件 |
| P3 | T6 弹性扩缩 | 需要任务切片 | 下一轮 |

**今晚建议：T1 + T2 + T3，正好覆盖"路由 / 性能 / 容错"三个基本面。**

T4 需要你先提供多个账号，否则测不出真实效果。

## 四、从测试数据到架构决策

每个测试的输出要能直接喂给设计决策：

| 测试结果 | 架构含义 |
|---|---|
| T1 路由准确率 < 100% | 能力注册表要更细，或加上下文判断 |
| T2 流式比批量快 14s | 必须做流式收集，不能批量等 |
| T3 掉线后任务全挂 | 需要心跳 + 超时 + 部分成功语义 |
| T4 加速比远低于 N | 限速按 IP 而非 key，要多出口部署 |
| T5 传递失败率高 | 需要专门的文件传输层 |
| T6 加机器无收益 | 任务粒度太粗，需要更细的切片 |

## 五、给开源项目的建议：最小可用架构

基于当前 SA 的局限，我建议的新增层次：

```
┌────────────────────────────────────────┐
│  SA（编排层）                          │
│  - 接收任务、理解意图                  │
│  - 决定拆不拆、怎么拆                  │
└──────────────┬─────────────────────────┘
               ↓
┌────────────────────────────────────────┐
│  节点注册表 + 能力路由（需要新建）      │
│  - nodes.json：谁在线、会什么、多少并发 │
│  - 心跳：节点定期上报                   │
│  - 路由：按 requires 匹配               │
└──────────────┬─────────────────────────┘
               ↓
┌────────────────────────────────────────┐
│  节点 Agent（每台机器上的 dsh）         │
│  - 接收任务描述                         │
│  - 自主决定用什么工具                   │
│  - 上报产物与状态                       │
└────────────────────────────────────────┘
```

**关键设计决策（有数据后再定）：**

1. **节点 Agent 用 dsh headless 还是专用 daemon？**
   - headless：零开发，但每次启动有开销（约 2-4 秒）
   - daemon：常驻，响应快，但要开发 + 处理生命周期

2. **能力是静态声明还是动态探测？**
   - 静态：手工维护 nodes.json，简单但会过期
   - 动态：节点自测后上报，复杂但准确

3. **产物怎么传？**
   - 经编排机中转：简单，但编排机是瓶颈
   - 节点直连：快，但 N² 连接复杂度

**这些都不该拍脑袋定，要靠测试数据。**
